# Upstream candidates

Log of changes on the `nura` branch that could go to zynthian upstream, and of upstream bugs
noticed but not fixed yet. The overview of what is already proposed is the description of
[PR #1](https://github.com/hjanetzek/zynthian-ui/pull/1); this file adds what came later.
Keep it up to date with each fix.

Status: **ready** (self-contained commit), **split** (mixed with port changes, needs its own
commit), **open** (noticed, not fixed).

## Bug fixes

| Commit | Status | Change |
|---|---|---|
| [85dbc36e](https://github.com/hjanetzek/zynthian-ui/commit/85dbc36e) | ready | **MIDI autoconnect fails for good after a MIDI device's port vanished; a failed snapshot load leaves the busy screen up.** `_midi_autoconnect()` logs a disconnected device as `logger.debug(f"... {devices_out[i].name}")`: the f-string is evaluated also without debug logging, and `.name` of an unregistered port raises (`cannot use string() on <cdata 'char *' NULL>`) before the slot is cleared, so every autoconnect from then on raises (the autoconnect thread every 100 ms; `load_snapshot`'s `request_midi_connect(True)` aborts the load). Fix: a name helper that tolerates gone ports. `load_snapshot()` ends its busy state only on its normal path: on an exception the busy screen stays at the last step ("restoring midi capture state", Duet 2026-11-09); now in `finally`. |
| [0a8e28b2](https://github.com/hjanetzek/zynthian-ui/commit/0a8e28b2) | ready (on the Duet since 2026-11-09; a race, one load since without a hang) | **zynmixer: deadlock removing a strip under pipewire-jack.** `removeStrip()`/`removeSend()` hold the mixer `lock` and wait for the process callback to drop the strip; `onJackConnect()` waits for that lock. pipewire-jack runs the connect callback with the client's process lock held (`jack.locked-process`, default on) and skips the process callback meanwhile, so a connect notification during a removal hangs both: loading a snapshot stuck at "removing mixer channel N from chain M" (Duet, 2026-11-09). With jackd, notifications run on their own thread and the process callback isn't blocked. Fix: `onJackConnect()` only tries the lock; if it is taken it marks the routing flags stale and the remove functions update them after releasing it. |
| [50d7d86a](https://github.com/hjanetzek/zynthian-ui/commit/50d7d86a) | ready | **Top bar: CPU load above 100 %.** The status colour fades from green to red with the load; above 100 % (pipewire-jack reports that at times) its green part went negative and Tk rejected the colour (`invalid color name "#cc-400"`) on every status refresh. |
| [fa23e789](https://github.com/hjanetzek/zynthian-ui/commit/fa23e789) | ready (the zynthian part; the APKBUILD line is port-specific) | **Audio recorder: jack_capture from PATH.** It started `/usr/local/bin/jack_capture`, where ZynthianOS installs it; distributions install it in PATH, so recording failed. | [effe2a4d](https://github.com/hjanetzek/zynthian-ui/commit/effe2a4d) | ready | **Restoring presets whose id is a list.** `set_preset()` with a preset_info looked the id up in the favourites as is; favourites are keyed by the id's string, and FluidSynth's ids are lists: `unhashable type: 'list'`, the preset of such a chain wasn't restored from snapshots. |

| [6de94330](https://github.com/hjanetzek/zynthian-ui/commit/6de94330) | split (with the admin settings below) | **Admin: PFL output list with an odd number of playback ports** raised `IndexError` (the pair loop read past the end). **Hotplug menu: the ZynVoice entry** paused autoconnect and returned without resuming it, so autoconnect stayed off. |

The accessors (`getSequence()` behind `getPlayState`, `getSequenceName`, ...) check the bounds but index vectors and return `Sequence*` without a lock, so a call from another thread during a load reads freed memory: SIGSEGV in `SequenceManager::getSequence` (Duet, 2026-11-07, three times when loading a snapshot, from the DrivenByMoss driver's own tick thread). zynthian's own drivers and screens poll on the threads the state manager serialises with the load, so they don't hit it; a controller driver with its own thread (or any ctypes user outside them) does. Safeguard for drivers: skip zynseq while `state_manager.is_busy()` (`"load snapshot"` is set for the whole load; saving and the other long operations set their own clients); that leaves a window for a call already running when the load starts. Proper fix: a reader/writer lock in `SequenceManager` (shared for the accessors, exclusive in `init()`, the scene and phrase changes and `setState()`), or a lock exported to Python that `load_snapshot` takes and threaded clients use. |
